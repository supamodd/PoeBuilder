# Архитектура 0.5

Самостоятельный C# / WPF проект; PoB не является зависимостью.

## Модели и миграции

`BuildDocument` schema 4 → nullable `PassiveTreePlan` → nullable `AscendancyPlan`, плюс nullable `EquipmentPlan` и `SkillPlan`. В основном плане: dataset ID, class index, main allocated IDs, attribute choices, manual limit. В дочернем: ascendancy ID, allocated IDs и отдельный manual limit. Deep-copy включает оба массива и словарь атрибутов.

Чтение schema 1/2/3 мигрирует в памяти до 4; файл не меняется до Save. Явные `null` в `tree`/`equipment`/`skills` считаются отсутствием данных, а не содержимым. Schema 1 с tree, schema 2 с ascendancy и любая legacy-схема с equipment/skills отвергаются, неизвестные поля не теряются. Новая схема намеренно не читается приложениями 0.3 и старше. Запись атомарна, `.bak` сохраняет предыдущее содержимое. Импорт/копирование создают новый GUID.

Структурная валидация не требует каталога: чужой dataset сохраняется без потерь, но выделение в нём заблокировано. Семантическая проверка проверяет совпадение набора, класса и восхождения, принадлежность ID, связность и лимиты.

## Снаряжение и умения (0.4)

`GameCatalog` — нормализованный снимок RePoE PoE2 4.5.5.2: 1845 баз (домены item/flask), 1294 обычных аффикса в пулах по базам, 300 вставок Rune/SoulCore/Idol, 1115 камней active/support/spirit. SHA-256 файла проверяется до разбора; dataset ID сверяется. Генератор `tools/prepare_catalog.py` — только для разработчика, приложение его не запускает.

Рядом лежит `affixes.json` (0.9.24, `AffixData`, генератор `build/extract-poe2-affixes.ps1`): 2739 обычных аффиксов с видом/уровнем/группами и **пулами по тегам спавна** плюс **9 баз самоцветов**. Он нужен потому, что пулы каталога собраны по тегу класса: аффиксы тегов вроде `str_armour` или `strjewel` и все базы `item_class: Jewel` из каталога недостижимы. `GameCatalog.ModsFor` = пул каталога ∪ пулы тегов базы (тег `default` не используется), `EquipmentRules.AffixCaps` применяет лимит PoB2 (самоцвет 2 + 2, прочее 3 + 3). Файл отсутствует — набор работает по-старому (каталог сам решает), поэтому старые данные не ломаются.

`GearItem` хранит BaseId, редкость (normal/magic/rare), ilvl, качество, ручное число гнёзд, ModRoll (ID мода + значения) и ID вставок. `EquipmentRules` проверяет: мод из пула базы и по ilvl, уникальность групп, диапазоны значений, лимиты аффиксов по редкости (0/1/3 на вид), эффект вставки для базы, посадку в слот, колчан-только-с-луком, двуручное оружие, лимит вставки (пустой/`1` — да, именованный семейный — отказ). Посадка уники, у которой нет базы каталога (её `BaseId` пуст: так приходит предмет из редактора и так его хранит старый файл), проверяется **по классу из таблицы PoB2**: `ResolveBase` подставляет базу по имени её базового типа (`Grand Regalia` → `Body Armour`), `UniqueBaseType` берёт тип из PoB2 или из строки базового типа в тексте предмета. Предмет без разрешимого класса отклоняется правилом (`PlanSlot`), а не падением: словарь баз больше нигде не читается через индексатор. `SkillRules` проверяет вид камня, уровень из списка камня, до 5 разных поддержек. Рекомендации поддержек — подсказка, не правило.

Планы не ссылаются на дерево; у каждого модуля своя `PlanHistory<T>` (50 шагов). Черновики редакторов (`ItemDraftViewModel`, `GroupDraftViewModel`) коммитятся только через правила; несохранённый черновик защищён запросом.

## Каталог дерева

Пинованный экспорт GGG 0.5.5, SHA-256 проверяется до разбора. Основное поле содержит прежние 4483 именованных записи, включая заблокированные специальные узлы. Artificial root исключён. Именованные восхождения из classes образуют 23 определения для 8 классов.

Каждое восхождение имеет **отдельный TreeCatalog** с dataset ID `<main-id>:asc:<asc-id>`. В него включаются только его узлы и внутренние рёбра, без моста к основному дереву. Внутри изолированного графа старт нормализуется к ClassStarts, а флаг IsAscendancy снимается для повторного использования общего движка. Исходные AscendancyId/IsAscendancyStart остаются в записи для аудита. Это не добавляет восхождения в основной allocator.

Abyssal Lich не имеет отдельного набора исходных узлов. Адаптер определяет исходный граф по overridePairs (Witch3) и применяет подстановки через отдельное определение Witch3b. ID выделений не заменяются ID вариантов описания. Номер экспортного снимка, версия приложения, схема файла и метка патча пользователя — разные значения.

## Движок

`PassiveTreeEngine` теперь использует multi-source **Dijkstra**, а не только BFS: обычные узлы стоят 1, безусловные free-узлы восхождений — 0. Старт бесплатен и не хранится в AllocatedNodes. Цена пути — сумма стоимости новых узлов, не его длина. Исходный план не изменяется при отказе. Снятие использует достижимость от старта и удаляет отключившиеся ветки, сохраняя альтернативные соединения.

`AscendancyRules` проверяет принадлежность классу и применяет дочерний план, не трогая основные выделения/лимит. Смена восхождения очищает только дочерние выделения; смена класса очищает оба графа. История хранит до 100 глубоких снимков полного плана и очищает redo после нового действия.

### Не подменять неполную поддержку полной

Multiple-choice, unlockConstraint, grants of passive/weapon points и другие специальные выделения по-прежнему блокируются. Free с условием тоже блокируется. Безусловный free стоит 0 при явном выборе пути; автоматическая выдача узла игрой не моделируется. Лимиты ручные, не вычисляются из уровня/испытаний. Счётчик не является доказательством игровой легальности всего билда. Эффекты узлов входят в экран «Персонаж» (безусловные статы).


## Расчёты v1 и экран «Персонаж» (0.5)

`CharacterCalculator.Calculate(build, tree, statMap, catalog)` — чистая функция без состояния: уровневые константы PoB2 (+12 жизни / +4 маны / +6 точности за уровень с базовыми смещениями `BaseLife+12·lvl`, `BaseMana+4·lvl`, базовая эвазия = 7; +2 жизни за силу, +6 точности за ловкость, +2 маны за интеллект), классовые базовые атрибуты из закреплённого экспорта дерева, строки выделенных узлов через `GameStatMap`, снаряжение активного набора (имплиты как максимум; локальные % на броню/уклонение/ЭС/блок/точность/скорость атаки/крит масштабируют только свой предмет), сопротивления с капом 75% (+ максимумы до 90%; эндгейм-база −60). Броня: честная оценка снижения A/(A+10·удар) против монстра уровня персонажа из `default_monster_stats`, кап 90%. Собственная регенерация маны — 4% от максимума в секунду.

Урон считается по каждой группе умений: атаки — от оружия (время атаки, физ. диапазон, крит оружия + локальные моды), заклинания — из поуровневых значений камня и его крита; бонус крит. урона по умолчанию 100% (крит ×2). Поддержки в v1 **не** изменяют урон — помечается `SupportsExcluded`. Выключенная группа помечается `DisabledGroup`; чужой набор оружия — `WrongWeaponSet`; нет оружия/данных — `NoWeapon`/`NoGemData`. Качество и конверсии урона не применяются и об этом сказано в UI.

`CharacterViewModel` пересчитывает сводку при каждом изменении плана (редактор/дерево/снаряжение/умения/уровень) и публикует её в `CalculationHub`. Экран «Персонаж» показывает ресурсы, защиту, атрибуты, сопротивления, по-групповой DPS и блоки «Не учтено» / «Допущения» — числовые строки без источника в UI не попадают.

## Иконки (0.5)

`IconService` читает `Data/Icons/manifest.json` (filesSha256/gemIcons/classFallback) и отдаёт замороженные BitmapImage (DecodePixelWidth 256) по статическому маппингу `Art/.../*.dds → Items/*.png`. Иконки предметов, камней и классов — арт GGG из публичных зеркал; распространение с приложением задокументировано в `Data/Icons/NOTICE.txt`, лицензионное решение за пользователем. Отсутствующая иконка — пустой слот с призраком класса, никаких заглушек-картинок. В 0.9.24 комплект вырос до 1794 файлов: добавлены 22 спрайта самоцветов (9 баз, 6 лиговых, 7 уникальных) и 417 спрайтов уников (128 px), которых до этого было 3 из 449.

`csproj` включает `Data/Icons/**` как Content (PreserveNewest). Дев-кэш `build/icons-src` в поставку не входит.

## WPF

Корневой `TreeViewModel` владеет полным планом и общей историей; дочерний `TreeViewModel` отображает только выбранное восхождение. Команды дочернего редактора фиксируются через родителя, undo/redo делегируются ему. `DisplayedTree` переключает граф, поиск, инспектор и ручной лимит. Список восхождений меняется с классом; синхронизация ItemsSource защищена от обратной записи промежуточного SelectedItem.

Выборы имеют явный DataTemplate(Name), а также безопасный ToString на доменных именованных записях. ComboBox/ComboBoxItem передают ContentTemplateSelector и ContentStringFormat. Это адресует замечание о выводе `TreeClass { Index = ... }` / `PassiveVariant { ... }`.

`ViewportSizing` вычисляет ширину поля из ширины колонки и высоты окна (запас 380 px на панели), высота = ширина × 9/16. **Дерево этим правилом больше не ограничено (0.9.25):** `ViewportSizing` остался в проекте (его поведение закреплено тестом `AscendancyTests`), но вкладка дерева занимает всю рабочую область, а управление лежит поверх вьюпорта — строка сверху, панель инструментов слева, карточка узла справа. Окно стартует развёрнутым (`WindowState="Maximized"`); доска слотов снаряжения масштабируется `Viewbox`-ом (`Stretch=Uniform`, `StretchDirection=UpOnly`), колонки редактора предмета пропорциональны.

`TreeViewport` использует DrawingContext, culling, кэш Geometry и CroppedBitmap. Камеры запоминаются отдельно по dataset ID, новый мини-граф автоматически вписывается. 31 портрет загружается локально из официальных классовых атласов: 8 основных и 23 восхождения. Основной фон меняется на выбранное восхождение; в мини-графе фон приглушён для читаемости связей.

Порядок отрисовки узла взят у PoB2 (`PassiveTreeView.lua:1064` — иконка, `:1126` — рамка **поверх** неё): атлас
`skills.png` хранит квадратные ломти с непрозрачным фоном, поэтому иконка рисуется первой и в долю ширины
рамки (`TreeFrameArt.IconShare`: 37/54 обычный узел, 54/80 нотабл, 82/120 кистоун, 76/76 гнездо, 54/100 узел
восхождения), а рамка — последней и во всю ширину. Иначе квадрат закрывал кольцо, и взятый узел терял своё
«подсвеченное» состояние. Наведение рисует панель сам вьюпорт (`BuildTooltip` + `DrawNodeTooltip`): чёрный
на 85 % лист с 1 px границей цветом PoB2 (`Tooltip.lua:88`, `:472-477`, `:656-671`), имя узла — на его же
шапке из `*passiveheader*.png` (`Tooltip.lua:18-32`, `:518-555`, набор по типу узла —
`PassiveTreeView.lua:1540-1546`, метрики в `TreeFrameArt.TooltipHeaderShape`); ниже — строки
модификаторов, состояние, набор оружия, содержимое гнезда и вклад в «Персонажа»; панель не
масштабируется зумом и разворачивается внутрь у края окна.

Клики узла — игровая модель: ЛКМ берёт узел вместе с путём в оба набора оружия и снимает его повторным кликом,
Shift+ЛКМ — в 1-й набор, Shift+ПКМ — во 2-й, ПКМ — только просмотр (`TreeViewport.OnMouseDown/OnMouseUp` →
`TreeViewModel.ClickNode(id, weaponSet)`). Набор записывается в `PassiveTreePlan.WeaponSetNodes` только после
успешного выделения и только для узла, которому PoB2 это разрешает (не кистоун, не гнездо, не восхождение —
`PassiveTreeView.lua:677-679`).

## Планер без расчётов (0.9.22)

**Решение:** проект — планер билдов (дерево, снаряжение, самоцветы, умения, награды актов, иконки).
Расчёты урона **заморожены**: `Calculation/*` остаётся как есть (v1 с честными «не учтено»), новые формулы
не добавляются, паритет с PoB2 по урону не ведётся. Работа идёт по `PLANNER-NEXT.md`, и каждый её пункт
обязан быть проверяемым (тест в ядре или `--check-windows`/скриншот в UI).

Уникальные предметы: `UniqueItemText` (ядро) — единственное место, где решается, **что написано у уники**:
вариант (`Selected Variant`, иначе последний — «Current»), отбор строк по варианту, имплиситы по
`Implicits: N`, диапазоны в максимум (`Resolve`; `UniqueTextParser.ResolveRanges` делегирует сюда, чтобы
правило было одно), сборка текста предмета и разбор чужого текста в строки с типами для показа.
Редактор предмета прав и на выбранной из каталога унике, и на импортированной (её текст авторитетен).
Модификаторы самой уники видны в общем списке «Добавки модов» (0.9.25): `UniqueItemText.PersonalMods` отдаёт
все строки данных, которых нет на предмете, вместе с именем варианта (у Morior Invictus их 29: «Spirit»,
«Life», «All Resistances»…). `ItemDraftViewModel.AvailableUniqueOptions` (отфильтрованный `UniqueLineOptions`)
наполняет ту же панель, что и аффиксы рера, а `AddUniqueLineCommand` кладёт выбранную строку
в текст предмета — оттуда её читает расчёт (`UniqueTextParser`). Поэтому «+10 to Spirit per Socket filled»
берётся одной кнопкой, а не поиском по вариантам.

Иконки: `ItemArt` (ядро) держит пути без WPF — свой арт уники из комплекта, арт её базового типа
(`GameCatalog.BasesByName` ищет базу по имени, которое называет PoB2), арт с публичного CDN, пустой слот.
`IconService` только грузит то, что ему дали; одна цепочка на редактор, снаряжение и самоцветы.

`--check-windows` (`WindowSelfCheck`) — разработческий ключ рядом с `--render-tree`: собирает редакторы
против закреплённых данных, раскладывает их вне экрана, прогоняет черновики и печатает результат с кодом
возврата. Причина: набор тестов работает на чистом .NET без WPF, поэтому ни один тест не может построить
модель представления с кистями и не увидит ошибку XAML. С 0.9.25 он проверяет и саму оболочку: раскладывает
`MainWindow` на 1920×1080 и 1280×800, требует, чтобы дерево занимало рабочую область, а панели и карточка узла
не схлопывались, следит за размером доски снаряжения и прогоняет клики дерева с наборами оружия, а также
пишет скриншоты вкладок в `%TEMP%\PoeBuilder-window-shots` — чтобы макет можно было посмотреть, а не только
посчитать.

## Регекс: генератор поисковой строки

Вкладка перед «Настройками». Она не часть плана: `RegexViewModel` читает только каталог и локаль, поэтому
работает и без открытого билда — ровно тогда, когда игрок ищет фильтр у торговца.

Строка собирается из **собственных шаблонов аффиксов закреплённого каталога**, а не из рукописных кусков:
`ItemFilterRegex` (ядро) получает текст модификатора и превращает его в шаблон поиска игры.

* `Fold` приводит шаблон к виду прокрученной строки предмета: диапазон в скобках — одно число
  (`+(10-20)%` → `+10%`), а цепочка «N to M» — два числа, которые предмет и показывает
  (`Adds 1 to (2-3)` → `Adds 1 to 2`).
* Слова экранируются, числа становятся `\d+`, а «е/ё» сворачивается в `[её]` — русский аффикс в игре пишется
  и так, и так. Свёртка обходит классы и экранирования, поэтому свой `[её]` не ломается.
* Границы «от/до» ограничивают **первое** число строки; второе остаётся открытым, потому что игрок не просил
  его трогать. Нечитаемая граница просто не применяется и помечается в интерфейсе.
* `Window` собирает класс символов на диапазон только там, где хвост свободен: `10-79` → `[1-7]\d`, а
  `10-20` пришлось разбить на ветви, иначе класс на позицию склеил бы окно в «10 или 20» и потерял 11-19.
* Логика: `All` — пробелы, `Any` — запятые, `Mixed` — обязательные плюс группа необязательных; `!`
  (исключение) сохраняется во всех режимах, потому что это отрицание, а не альтернатива.
* Счётчик идёт к лимиту игры в 250 символов; переполнение показывается, а не обрезается молча.

## Выдвижная левая панель

**Решение:** панель вкладок запускается свёрнутой — только значки; названия вкладок, логотип с версией,
карточка текущего билда и подпись «Независимый проект» выезжают под курсор и уходят обратно, когда он
уходит. Состояние одно — `MainViewModel.NavExpanded`, его меняют `SidebarEnter/SidebarLeave/
SidebarLostKeyboardFocus` (`MainWindow.xaml.cs`): раскрытие держит любой из двух входов — мышь или фокус
клавиатуры, — поэтому ни один из них не может закрыть панель под неподвижным курсором или под элементом,
оставшимся в фокусе.

**Как устроено:** колонка рабочей области — `Auto`, ширину задаёт сам `Border` (`SidebarHost`). Всё, что
двигается при раскрытии, читает одну величину `SidebarFoldState.Progress` (0…1): ширина 64→245 px, поля
0→18/22/18/18, центровка значков и логотипа и прозрачность названий. `SidebarFoldConverter` переводит прогресс
в эти четыре величины, `MainWindow.AnimateNav` двигает его `DispatcherTimer`'ом с кубическим easing: на
раскрытие 190 мс ease-out, на складывание 150 мс ease-in-out. Ширина колонки `Auto` вместо числа означает,
что рабочая область просто забирает остаток окна.

**Графика и значки.** Логотип панели и иконка приложения — файлы владельца в `assets/`
(`poebuilderLOGO.0.7.png`, `poebuilderICON0.7.ico`), подключённые в `.csproj` как `Resource`: первый рисуется
`Image` в слоте 37×43 (`Stretch="Uniform"`), второй попадает и в `ApplicationIcon` exe, и в `Icon` окна.
Значки вкладок лежат в `assets/NavIcons/<NavKey>.png` (слот **19×19**, обводка по центру) и подхватываются
по имени ключа вкладки: `NavItem.Glyph` проверяет наличие ресурса и отдаёт `ImageSource`, иначе разметка
показывает встроенную геометрию `NavItem.Icon`. Проверка обёрнута в `try/catch` намеренно: `GetResourceStream`
бросает исключение на отсутствующей части, а не возвращает `null`. Так набор можно пополнять по одной
иконке, и панель не ломается на неполном наборе. Подробности отрисовки — в `assets/NavIcons/README.md`.

Почему прогресс, а не `DataTrigger` по булеву флагу: триггер меняет ширину на одном кадре, а подписи по
`BoolVisibility` — на другом, и центровка иконок скачком уезжает на третий. Панель выглядит дёрганой не из-за
длительности, а из-за того, что части приходят не одновременно. Ещё `ClipToBounds="True"` на `SidebarHost`:
названия остаются в разметке и их **выдаёт расширяющийся рельс**, а не мигание видимости. `NavExpanded` в
модели остаётся как состояние, но разметка его больше не читает — источник истины по движению один.

Почему `DispatcherTimer`, а не `DoubleAnimation`: публичного `BeginAnimation` в WPF нет — метод живёт на
внутреннем `AnimationStorage`, а `Storyboard` требует живой визуальный элемент. Тик вручную заодно решает
переход на лету: новая цель стартует от текущего значения, поэтому прерванное складывание продолжается с
текущей ширины, а не прыгает.

**Проверка:** `--check-windows` требует, чтобы `SidebarHost` был уже 100 px в сложенном виде, шире 200 px
после `SetNavExpandedImmediate(true)` и снова сложился обратно, и кладёт скриншот раскрытой панели в
`%TEMP%\PoeBuilder-window-shots\sidebar-expanded.png`. Проверка ставит состояние через `SetNavExpandedImmediate`:
раскладка в проверке синхронная, идущая анимация дала бы панель, измеренную на полпути.

## Текст, ресурсы и будущие модули

Локализуется UI; игровые строки по-прежнему EN. Полного проверенного RU-набора нет, автоперевод не применяется. Это незакрытое требование, не готовая локализация.

Происхождение и хеши данных/изображений — в manifest, права GGG не включены в MIT. Нет сетевых вызовов, чтения установленного клиента или PoB-кода. `UnavailableCalculationEngine` (контракт ICalculationEngine) остаётся как честный «нет данных» бэкенд; реальная математика v1 живёт в CharacterCalculator и не претендует на полноту.

Снаряжение и умения реализованы по `EQUIPMENT-NEXT.md` (статус — в самом файле). Расчёты и адаптеры чужих форматов должны жить отдельно от MainViewModel. Не добавлять фиктивные предметы или числа ради заполненного интерфейса.

## Локализация игровых данных

`Data/Game/locale-ru.json` создаётся и хранит русские строки для дерева, гемов, баз и уникальных предметов (`names`, `tree`) и для текста модификаторов (`mods`). Моды сопоставляются по СОБСТВЕННОМУ английскому шаблону, а не по позиции в странице: архив `Data/DataBase mods` пишет диапазон как `(1—2)`, а каталог — как `(1-2)`, и разделяет их одним пробелом, поэтому `GameStrings.FoldKey` снимает все пробелы, приводит тире к одному символу и регистр к нижнему. Совпадение берётся только при точном равенстве свёрнутых строк, поэтому мод без перевода остаётся английским, а не получает чужой перевод. Перевод меняет только отображение: ID, значения и расчёты остаются английскими.

`GameStrings.Clean` убирает из строки стата машинный ID вида `[Allies|Союзники]`, оставляя читаемую часть: расчёт опознаёт стат по ID, но печатать ID игроку незачем.

Моды сопоставляются по СОБСТВЕННОМУ английскому шаблону, а не по позиции в странице, и в четыре прохода: точное совпадение, совпадение по разделителям стат (`; `, перевод строки, ` + `, ` | `), совпадение по форме с подстановкой наших чисел и сборка из переведённых стат по отдельности. Каждый результат проходит проверку чисел: русская строка обязана содержать те же числа в том же порядке, что и английская, иначе перевод отбрасывается и мод остаётся английским. Покрытие: 1668 модов из 2183; оставшиеся — луки, гранатомёты и редкие классы, которых нет в архиве.

Пересборка: `build/extract-poe2db-ru.ps1`, затем `build/extract-mods-ru.ps1`.
