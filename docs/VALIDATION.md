- **3. `KeyNotFoundException` при добавлении Morior Invictus (ваш `error.log`, 21:26).** Стек в журнале:
  `EquipmentRules.Validate` → `EquipmentPlan.cs:161` → `Dictionary.get_Item('')`. Причина: уника из

## 0.9.24 (все моды снаряжения и самоцветов, базы самоцветов, арт уников локально)


Запрос: «добавляй все моды снаряжения, самоцветов, иконки-изображения для них». Работа сделана на данных
закреплённого снимка, ничего не выдумывая: то, чего в снимке нет, помечено как отсутствующее.

- **Моды снаряжения: измеренная дыра — 30 009 пар «база × мод», и она закрыта.** Каталог собирает пулы по
  тегу класса, поэтому `LocalArmourAndStunThreshold1` (катится на `str_armour`) не лежал ни в одном пуле:
  Strength-нагруднику этот мод был недоступен, хотя мод есть в самом каталоге (проверено: `catalog.mods`
  содержит его, `modPools['pool-2']` — нет). Точный замер (замыкание по тегам баз, только prefix/suffix
  домена `item`, без essence-only, без `grants_effects` и без `adds_tags` — те же фильтры, что документирует
  `THIRD-PARTY-NOTICES`) дал **30 009** таких пар: броня, щиты, фокусы, перчатки, сапоги, шлемы и оружейные
  классы. Новый скрипт `build/extract-poe2-affixes.ps1` выгружает `Data/Game/affixes.json` (0.69 МБ,
  sha256 `22d4ba00…e06f`) с **2739 аффиксами** (1326 prefix / 1099 suffix — 1200 из них каталог уже знал,
  1539 нет) и **пулами по 61 тегу спавна**. `GameCatalog.ModsFor` теперь = пул каталога ∪ пулы тегов базы
  (тег `default` намеренно не используется: RePoE даёт его как «зонтик», из-за него к любой базе липли
  catch-all моды). Обрезка `Take(200)` в редакторе предмета убрана; вид/уровень аффикса показываются в списке.
- **Самоцветы: 9 баз из снимка, свой пул, лимит 2 + 2.** В `base_items.json` снимка есть `item_class: Jewel`
  (Ruby, Emerald, Sapphire, Diamond, Timeless Jewel, Time-Lost Ruby/Emerald/Sapphire/Diamond) с их путями
  арта `Art/2DItems/Jewels/*.dds`; в каталог они не попали, поэтому валидация знала только «безымянный»
  самоцвет. Теперь базы грузятся из `affixes.json` (`Catalog.Bases` и `BasesByName` их видят), аффиксы
  самоцветов получают **вид и уровень** (в снимке они не в домене `item`, а в `misc` — отбираются по тегам
  баз самоцветов: `strjewel`, `dexjewel`, `intjewel`, `*_radius_jewel`), а пул — из тегов базы
  (`strjewel` = 49, `dexjewel` = 73, `intjewel` = 55, `*_radius_jewel` = 48/53/72). Лимит аффиксов взят у
  PoB2 (`Classes/Item.lua:1303`: `affixLimit = ((self.type == "Jewel" …) and 4 or 6)`), то есть **2 префикса
  + 2 суффикса** у самоцвета, 3 + 3 у прочего; `EquipmentRules.AffixCaps` применяет это в валидации, а
  редактор использует тот же метод, чтобы лишнего не предлагать. Важная деталь: у самоцвета теперь есть и
  проверка «аффикс из своего пула» — армейский префикс на Ruby отклоняется (`PlanModInvalid`).
- **Иконки: комплект вырос 1355 → 1794 файла (9.0 → 20.1 МБ).** Добавлено 22 спрайта самоцветов (9 баз,
  6 лиговых, 7 уникальных) и **417 спрайтов уников** — до этого локально было **3 из 449**, и уник
  показывался артом базового типа. Причина не в лени: пинованный путь PoE2 на публичном CDN
  (`https://web.poecdn.com/image/Art/2DItems/Jewels/RubyJewel.png`) отвечает **404** (проверено и на
  известном базовом пути `…/Rings/Basetypes/IronRing.png` — тоже 404), то есть «загрузка на лету» не
  работала. Спрайты взяты из того же пинованного миррора, что и прежний комплект
  (`josh-dastmalchi/exiledata-assets @ 3354944d`, 2DItems как WebP), декодированы разово вне решения
  (`SixLabors.ImageSharp` 3.1.5 + PNG): на этой машине **нет WebP-кодека** — `WIC` отвечает «не удалось
  обнаружить компонент обработки изображений», поэтому декодирование нельзя было сделать скриптом. Размер:

## 0.9.23 (отзывчивость дерева: 100×, фон классов как в PoB2, падение на наведении)




Три замечания с одного запуска: дерево «залипает» при отдалении, картинки классов в центре «криво и
мыльно», падение `TreeRuleException: TreeInvalidSaved` при простом движении мыши по дереву
(`error.log`: `TreeViewport.OnMouseMove` → `MainViewModel.InitializeAsync` → `CharacterViewModel.NodeImpact`
→ `PassiveTreeEngine.RefundSet` → `Validate`, `PassiveTreePlan.cs:179`).

- **Панорамирование: 7.8 с на кадр → 0.07 с, причина измерена, а не угадана.** Инструмент — свой ключ
  `PoeBuilder.exe --render-tree --no-fit --frames N --zoom z`, который рисует кадр в `RenderTargetBitmap`
  (то есть программным растеризатором) и печатает медиану. Разбор по слоям («зонд» на время отладки:
  недоход до слоя узлов / только связи / только бэкдропы) дал: 11 бэкдропов и ~9 000 связей — **49 мс**
  вместе, а проход 877 видимых узлов — **7.4 с**, то есть ~8 мс на узел. Замена `PushOpacity(…) + DrawImage`
  на отрисовку без группы (тот же кадр, те же картинки) дала **0.49 с**, разница в 15 раз — это и есть
  ответ: программный растеризатор WPF заводит под каждую группу прозрачности отдельную поверхность.
  Исправление: `TreeViewport.DrawArt` рисует арт кистью с прозрачностью (`ImageBrush.Opacity`, кэш по
  `(арт, процент)`) — для узла это рамка, значок и узор мастери. Итог на 1640×918: **0.13 → 0.070–0.087 с,
  0.35 → 0.059–0.065 с, 0.7 → 0.077–0.080 с** (было 7.81 / 7.64 / 7.66 с). Вид кадра не изменился
  (снимки `--render-tree --at 0,0 --zoom …` до и после совпадают по композиции).
- **Фон класса: убрано лишнее изображение, а не подобраны коэффициенты.** В центре рисовались арт PoB2
  (`Classes…`, 1500 юнитов) и поверх него **портрет из `Data/Tree/Portraits`** в квадрате 2800 юнитов —
  отсюда видимая граница квадрата (скриншот `--at 0,0 --zoom 0.35`: тёмный прямоугольник поверх круглого
  арта) и «мыло» (портрет 640 px растягивался на ~1 000 px и больше). Теперь для главного дерева рисуются
  ровно слои PoB2 (`DrawClassBackdrops`: кольцо восхождений, арт класса в центре, `BGTree`, повёрнутый
  `BGTreeActive`), а портрет — **фолбэк**, когда арта PoB2 в наборе нет, и фон **вида восхождения**: у
  графа восхождения собственные координаты (проверено по данным: узлы `Witch1` лежат в
  `x[-1628..351] y[-18939..-17081]`, а позиция арта восхождения в таблице — `(-9132,-12570)`), поэтому
  арт там пришлось бы подгонять под граф, а портрет по границам графа ложится сам и он резче.
- **Арт пересобран резче, скриптом в репозитории.** `build/extract-tree-art.ps1` уменьшает
  полноразмерные PNG (те самые срезы BC7-атласов, см. 0.9.17) в `Data/Tree/Art/class`: **512 px** базовые

## 0.9.22 (планер: уники с вариантами, иконки уников, заморозка расчётов)

Решение зафиксировано: проект — **планер билдов** (дерево, снаряжение, самоцветы, умения, награды актов,
иконки). Расчёт урона и прочие расчёты **заморожены на неопределённое время**: формулы v1 остаются как
есть, новые не добавляются, паритет с PoB2 по урону не ведётся. Каждый следующий шаг — про полноту и
наглядность плана, и он обязан быть проверяемым.

- **Модификаторы уников.** Ядро получило `UniqueItemText`: вариант, который использует игра
  (`Selected Variant`, иначе последний — «Current»), отбор строк по варианту, разделение имплиситов по
  `Implicits: N`, перевод диапазонов `(30-40)` → `+40` (та же функция, что и у импортёра расчёта: одна
  реализация вместо двух), сборка текста предмета и разбор чужого текста обратно в строки с типами.
  Проверено на данных: The Anvil (3 варианта, вариант 1 против «Current», первая строка — имплисит),
  Morior Invictus (много вариантов, текст одного варианта не равен тексту другого, полный round-trip
  «собрали → разобрали → те же строки»), импортированный текст (имя, база, объявленный имплисит,
  свойство остаётся свойством, `--------` и пустая строка не дают строк).
- **Редактор предмета.** Выбор варианта, строки выбранного варианта с правкой значений, пометки «вариант
  N» / «тег: …», автоматическая сборка текста (заметок) из строк, превью-тултип уники в цветах игры —
  раньше панель превью для уники была пуста. Для импортированной уники строки берутся из её собственного
  текста (он авторитетен), для выбранной из каталога — из данных PoB2.
- **Иконки.** `ItemArt` (ядро, без WPF) держит всю логику путей: свой арт уники из комплекта → арт её
  базового типа (PoB2 называет базу) → арт с публичного CDN → пустой слот; неизвестное имя не даёт
  заглушки. `GameCatalog.BasesByName` даёт доступ к базе по имени (уника называет базу текстом, импорт —
  вторую строку). Редактор предмета, список снаряжения и самоцветы используют одну и ту же цепочку: у
  уника, выбранного в редакторе, иконки не было вовсе, а импортированный уник без опознания в каталоге
  показывал пустое место.
- **`--check-windows`** (скрытый ключ, `WindowSelfCheck`): собирает редакторы против закреплённых данных,
  раскладывает их вне экрана, прогоняет черновики (включая **сохранение** предмета, то есть настоящие
  правила снаряжения) и печатает строку на проверку. Прогон: **14 проверок**, «WINDOWS: every layout
  loaded», код возврата 0, журнал не вырос, одинаково в Debug и Release. Он же проверяет то, чего не может
  набор тестов (он работает на чистом .NET без WPF и не увидит ошибку XAML). Окно, черновик которого уже
  изменён, остаётся открытым: закрытие вызвало бы вопрос редактора «сохранить черновик?», а отвечать в
  скриптовом прогоне некому — поэтому процесс завершается без «мягкого» закрытия окон.
- **Проверки:** **210/0** в Debug и Release (206 прежних + 4 новых: варианты/строки уники, round-trip
  текста, разбор импортированного текста, пути иконок и наличие манифеста комплекта). Приложение
  запускается, `error.log` не растёт. Сборка без ошибок и предупреждений.
- **Что сознательно не сделано:** строки уники пока живут как текст предмета (заметки), а не отдельным
  полем схемы — это следующий пункт (схема 5) в `PLANNER-NEXT.md`; арт уников, который берётся с CDN, не

## 0.9.19 (скорость в отчёте разложена по источникам; семейство `attack_and_cast_speed_+%`)

- **Отчёт теперь показывает, из чего собран пул скорости, а не только его сумму.** PoB2 считает скорость
  скилла как `1 / (baseTime / round((1 + inc/100) * more, 2))` (`CalcOffence.lua:2835-2840`), а его же экспорт
  содержит **одно число панели и никакой разбивки** — поэтому расхождение нельзя было разобрать. Теперь
  `StatBucket` записывает источник каждого вклада (`AddCastSpeed`/`AddAttackSpeed`/`AddSkillSpeed`/
  `AddTotemCastSpeed`), а отчёт печатает `Pool:CastSpeedSrc:<id>`, `Pool:SkillSpeedSrc:<id>`,
  `Pool:TotemCastSpeedSrc:<id>`, `Pool:AttackSpeedSrc:<id>`. Плюс исправлен порядок: снимок `Pool:*` берётся
  **после** всех проходов (дерево, предметы, баффы, условия), то есть печатает то, что реально читает цикл
  скиллов; раньше он брался до проходов, и `Pool:CastSpeedInc = 128` был бледной копией настоящих `156`.

  `Pool:CastSpeedInc = 156` — и **весь он** из одного id: `Pool:CastSpeedSrc:base_cast_speed_+% = 128`
  (предметные и древесные «N% increased Cast Speed») плюс два условия `+20` (Low Life) и `+8` (Crit Recently);

  исправлению, найденный инструментом, а не догадкой.
- **Арифметика остатка (для следующего шага, чтобы не искали заново).** Панель PoB2 даёт

- **Семейство `attack_and_cast_speed_+%` теперь применяется.** PoB2 мапит его в `mod("Speed","INC")` без

- **Пять тотемных/скаутных термов PoB2 каталогизированы с числами, а не применены в полсилы.**

## 0.9.17 (рамки узлов дерева из арта PoB2, «Gain X% of Damage as Extra Y» для уникальных предметов)

- **Рамки узлов дерева — теперь арт PoB2, а не наши эллипсы.** PoB2 рисует узел как спрайт рамки плюс
  иконку умения поверх (`Classes/PassiveTree.lua:506-540`), а спрайт выбирается по типу и состоянию узла из
  `nodeOverlay` (`TreeData/0_5/tree.json`): обычный узел — `PSSkillFrame` / `PSSkillFrameHighlighted`
  (узел на пути клика) / `PSSkillFrameActive` (выделен), нотабельный — `NotableFrame*`, гнёзда самоцветов —
  `JewelFrame*`, кистоуны — `KeystoneFrame*`, узлы восхождения — один набор 208×208 для всех классов.
  Каждый спрайт — **срез BC7-атласа (DDS array), а не область внутри картинки**: в `ddsCoords` номер среза и
  есть индекс спрайта (`group-background_152_156_BC7.dds.zst` → `NotableFrameAllocated = 13`), а размеры
  среза совпадают с именем атласа (104×104, 152×156, 220×224, 208×208).
- **Одноразовая конвертация, приложение по-прежнему без зависимостей от BC7.** `zstd -d` распаковывает
  `.dds.zst`, затем инструмент вне решения (`BCnEncoder.Net 2.1.0`, `net10.0-windows` + WPF
  `PngBitmapEncoder`) пишет по одному PNG на срез: `treeart <file.dds> <outDir> <slice:Name> ...`.
  Срезы равного размера идут сразу за 148-байтовым заголовком, поэтому шаг среза = `(длина − 148) / arraySize`
  (сходится с `dwPitchOrLinearSize`: например 104×104 → 14 656 байт на срез, 6 срезов, 148 + 87 936 = 88 084 =
  длина файла). Готовые PNG лежат в `src/PoeBuilder.App/Data/Tree/Art/` (15 файлов), маппинг и размеры — в
  `Core/Tree/TreeFrameArt.cs`; тест сверяет и имена, и фактические размеры PNG с размером среза.
  Проверка «это рамка» численная: у рамок центр прозрачный (0 из 81 пикселя), у гнёзд самоцветов — залит (81 из 81).
- **Связи (орбиты и коннекторы) — тоже арт PoB2, и он ложится аффинно.** Спрайты связей — обычные PNG
  (`TreeData/0_5/Character_orbit_*.png`, 30 файлов ≈ 4 МБ в `Data/Tree/Art/orbit/`). Измерения по пикселям
  дали то, чего нет в документации: орбитальный спрайт — это **дуга 90° с центром в правом нижнем пикселе
  изображения**, и радиус арта совпадает с радиусом орбиты (`Character_orbit_normal1.png`: 1333×1333,
  R = 1318.4 ± 4, каталог орбиты — 1322; `…normal9.png`: 91×90, R = 81.7, орбита — 82). Поэтому связь
  кладётся **аффинным преобразованием**, а не «кайт»-квадом, который PoB2 растягивает: масштаб
  `радиус орбиты / радиус арта`, поворот так, чтобы биссектриса дуги встала на середину промежутка, и
  перенос правого нижнего пикселя в центр орбиты. Дуга шире 90° делится на части, каждая часть
  подрезается клином по своему угловому сектору (PoB2 вместо этого сдвигает два угла квада — у нас это
  точная операция, а не приближение). Линейный спрайт — полоса 1435×29 с видимой лентой 11 px: рисуется
  прямоугольником вдоль отрезка с тайловым `ImageBrush`, то есть повторяется каждые 1435 юнитов, ровно как
  PoB2 (`endS = distance / art.width`). Индекс спрайта — **не формула**: PoB2 берёт файл, чей радиус
  совпадает с радиусом орбиты (орбита 3 → спрайт 6, орбита 7 → спрайт 7), и это зафиксировано таблицей.
  Тест проверяет самое важное: точки дуги арта после преобразования попадают **точно на окружность орбиты**
  (расхождение < 0.01 юнита), размеры всех 30 файлов, отношение радиусов арт/орбита (2–3 %), разбиение углов
  и наклон линейной полосы. Если спрайтов нет — остаётся прежняя обводка геометрии.

  и `AttackDamageMoreFactor` — множитель в `AttackSplit`). Базлайн Flameblast вернулся к 17 210.6 (0.00 %).
- **Найдена и исправлена вторая ошибка: бифуркация критических ударов затиралась.** Garukhan's Resolve даёт
  «Critical Hits Bifurcate»; PoB2 (`CalcOffence.lua:3824-3843`) считает `conditionalChance = (pre²/100)/post`
  и применяет это как **MORE** к крит-множителю (`extraDamage = damageBonus + conditionalChance × damageBonus`).
  У нас множитель вычислялся на строке выше и **перезаписывался** присваиванием `critBonus = (Base + …) × …`.
  Теперь он идёт в `critBonusMore`: крит-множитель Twister **×8.68 → ×11.24**, DPS 943 257 → **1 211 164**,
  эффективный DPS 1 683 706.
- **Like-for-like сравнение с PoB2.** Фикстура выгружена в режиме EFFECTIVE
  (`<Input string="EFFECTIVE" name="misc_buffMode"/>`), поэтому её `AverageDamage`/`TotalDPS` уже включают
  модификаторы врага. Тест теперь печатает и проверяет сравнимые величины: **эффективный удар 92 579.1**
  против «49 447-148 577» PoB2 (среднее 99 012) = ×1.069, **эффективный DPS 1 683 705.6** против 2 049 501.9 =
  ×1.217. Раньше мы сравнивали сырые числа с эффективными и «остаток» выглядел как ×2.26.

- **Rage даёт урон** (`Modules/CalcPerform.lua:777-791`), и он теперь считается: количество берётся из
  инпута `multiplierRage` (PoB2 показывает его только когда билд может набирать ярость, в подсказке —
  «inherently grants 1% More Attack Damage per 1 Rage»), ограничивается максимумом
  (`Data/Misc.lua:123 ["BaseMaximumRage"] = 30` + «+N to Maximum Rage»), а затем превращается в
  `RageEffect = floor(stacks × (1 + RageEffect INC / 100))` и уходит в `Damage MORE` **для атак**. У Twister
  30 ярости и 75 % усиления силы от **Berserk** (`act_str.lua:1508`: `skill_base_rage_effect_+%_to_apply` →
  `mod("RageEffect","INC")`) → `floor(30 × 1.75) = 52` → **×1.52 к урону атак** (было 0). Проверено: при
  `RageStacks = 0` хит падает ровно в 1.52 раза.
- **Elemental Conflux** (`ConfigOptions.lua:389-407`): «Average» (умолчание) даёт каждой стихии **+25 % more**

  выбранной стихии она получает все 75 %, остальные — ноль. Проверено по долям: молния ×1.4, огонь ×0.8.
- **Trinity** (`ConfigOptions.lua:673`): `configResonanceCount` (0..300) → `Multiplier:ResonanceCount`, а
  statMap камня делит на 30 (`div = 30`, хотя текст стата говорит «per 50») → 300 резонанса = 10 стеков × 6 % =
  **+60 % more к каждой стихии** (хит 61 663.9 → 92 061.3). У фикстуры Twister инпута нет, поэтому на её числа
  это не влияет — но механика работает, как только резонанс задан.
- **Три «тихие» потери мод в разборе данных, из-за которых этот блок не считался:**
  1. `ConditionName` читал `var = "…"` **следующего** тега как переменную текущего (у
     `{ GlobalEffect, effectName = "…" }` перед `{ Multiplier, var = "…" }`), условие становилось «неизвестно»
     и мод отбрасывался — теперь имя берётся только из своего тега;
  2. одна строка statMap может содержать несколько вызовов `mod(...)` (Conflux — три стихии), а разбирался
     только первый: появился `PoB2ModTranslator.ParseAll`, и каждый вызов оценивается по **своим** тегам;
  3. множители с `invert`/`div` применяются к значению, а их теги (`Multiplier`/`MultiplierThreshold`/
     `StatThreshold`) снимаются перед передачей мода в sink.
